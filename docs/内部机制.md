# 内部机制

本插件的架构与实现要点。想改行为前先读这里，能少踩很多坑。

## 一句话架构

> QQ 消息进 → 中间件链过滤与富化 → 组装成用户消息投给 dsh agent → agent 的 session 事件出 → 转成 QQ 消息发回。

宿主半（Node）与浏览器半（Web Bundle）分离：宿主半负责连接、协议、状态机；浏览器半只在设置页里渲染界面。

## 中间件链的顺序（关键）

顺序不是随便排的，改动前先理解每一步的职责：

| # | 中间件 | 作用 | 位置为什么重要 |
|---|--------|------|----------------|
| 1 | `errorHandler` | 错误兜底 | 最外层 |
| 1.5 | `chainSentinel`（本插件） | **丢弃留痕哨兵** | 必须紧跟 errorHandler，才能包住后面所有关卡；下游任何 `ctx.stop()` 都会让它读到原因并落盘 |
| 2 | `messageFilter` | 去重 + 机器人回声过滤 | 按 `messageId` 去重，不会误杀不同群的同文消息 |
| 3 | `accessPolicy` | 白名单 / 开放 / 禁用 | — |
| 4 | `historyBuffer` | 群历史缓冲 | **必须在门控之前**：未点名她的群消息也要进上下文 |
| 5 | `mentionGate` | 记录 `wasMentioned` | 自主接话开启时改为 `passthrough`：只标记不拦 |
| 5.5 | `proactiveGate` | 自主接话判定与拦截 | **必须在 mentionGate 之后**：那里才写 `ctx.state.mention` |
| 6 | `contentSanitizer` | 去 @marker、表情标签、空白 | — |
| 7 | `rateLimiter` | 三层限流 | — |
| 8 | `slashCommand` | 斜杠命令 | 在并发守卫之前，命令不排队 |
| 8.5 | `questionAnswer` | 待答问题截获 | 同上，否则「等答案 ↔ 答案被缓冲」死锁 |
| 9 | `concurrencyGuard` | 同 peer 串行 + 消息合并 | 按 `scope:targetId` 隔离，不同群互不影响；`onMerge` 负责「合并了几条」的留痕 |
| 10 | `typingIndicator` | 输入中提示 | — |
| 11 | `quoteRef` | 引用消息解析 | — |
| 11.5 | `attachmentProcessor` | 附件下载 | — |
| 12 | `envelopeFormatter` | 上下文组装（history + quote + sender） | — |

**改中间件顺序前先看这张表**。`proactiveGate` 与 `mentionGate` 的相对位置尤其关键：反了就读不到 `wasMentioned`，自主接话会永远判成「被点名」或「完全没被点名」。

### 图片怎么进模型（2026-10-23 修）

群里发的图片由 `attachmentProcessor` 下载到 `~/.dsh-qqbot/media/`，但**只下载不发图**
等于没接——模型看到的是一行 `- Image: C:/.../xxx.png` 路径，只能回「我看不懂」。

现在入站侧把下载好的图片转成 dsh-llm 的 `ImageBlock`，**作为多模态块附在用户消息上**
（`media/image-input.ts` + `SessionManager.buildInlineImages`），图片在前、文字在后。

两道闸，任一不过就退回「只给路径」的老行为：

1. **当前模型必须接受图片输入** —— 查 `resolveModelInfo().inputModalities.includes('image')`。
   不查就附会让**整轮直接失败**（与 `reasoningEffort` 同一类坑）。
   DSH 自己的 ACP 代码用的是同一个判断，语义一致：`undefined` 是未知、显式不含 `image` 是负能力
2. `attachments` 服务必须可用（启动时在 `startup.log` 留痕）

**为什么不用 `qqbot_describe_image` 工具**：`qqchat` 是零工具预设，且 persona 明写
「不读写文件」——工具在这条通道上根本用不了。这与 M4 群友档案、M5 表情包是同一个约束。
直接附图不需要工具，反而更贴合零工具设计。

## 会话隔离

会话键：

```
qqbot:${appId}:${kind}:${peerId}
```

- `kind`：`c2c`（私聊，peerId = 用户 openid）| `group`（群聊，peerId = 群 openid）
- 私聊与群是**两条独立会话**：在群里聊过的上下文不会带到私聊
- 群历史缓冲另有独立键（`${appId}:${groupOpenid}`），回复后清空，避免下次组包重复

## 预设（默认 qqchat，可切换）

会话默认跑在 `qqchat` 预设上（零工具 + 插件内置人格），但**支持切换**。

解析优先级（`model/preset-resolution.ts`）：

```
per-peer 偏好（/preset 切换）  >  config.preset  >  qqchat
```

- 回落**必须**到 `qqchat`，不能落到宿主默认 preset——那会带来终端与文件工具，
  直接违背零工具设计
- 切换 = 持久化偏好 + **重建会话**：`agents.resume()` 改不了 preset（只接受
  `agentOptions` 与 `setup`），已实测证实
- **两个概念必须分开**（`prefs-store.ts`）：
  - `presets` = 用户选的偏好
  - `sessionPresets` = 会话实际创建时用的 preset（一致性检测用）

  混用会导致「刚切换完就被自己的一致性检测丢掉」——切换写偏好，
  而检测要拿会话真实跑的来比
- `/preset` 是**管理员专用**命令（切到带工具的 preset 是安全相关操作）

预设定义在插件自带的 `cordis.patch.yml`（`preset-qqchat` 插入行）里，用户装上即生效；profile 层仍可按同 id 覆盖。

`qqchat` 的要点：**不挂 `persistent-shell`（bash/pwsh）与 `tool-fs`**，工具清单里没有终端、没有文件读写；`persona.complete=true` 表示那段 prefix 直接作为完整 system prompt。

## 拟人化的落点

| 能力 | 位置 | 做法 |
|------|------|------|
| 不每条都回 | `shared/skip-marker.ts` | 回复恰为 `[skip]` → 不发送、不计入回复统计 |
| 不秒回 | `transport/reply-delay.ts` | 基础 + 每字 + 随机抖动，封顶可控 |
| 不复读自己 | `features/anti-repeat/` | 记自己最近 5 条发言，前置进上下文让其换说法（**预防式**，不额外跑模型） |
| 记得谁是谁 | `features/people/` | 昵称 + 别名 + 互动次数，注入一小段旁白 |
| 择时开口 | `features/proactive/activity.ts` | 连发 / 她刚说过话 / 群太热闹 → 加减分 |
| 表情包 | `features/stickers/` | 从回复文本推断情绪 → 按规则选图 → 发送 |

开关都在设置页里（「QQ 机器人 → 自主接话 / 回复节奏 / 群友档案 / 防复读」），改完自动重载。
表情包默认关闭，需先自备素材（见 [表情包.md](表情包.md)）。

## 设置页能改什么

宿主半的 `setup/bind-routes.ts` 里有一份**可编辑配置白名单**（`EDITABLE_CONFIG_KEYS`），
白名单外的字段只能改 `cordis.patch.yml`：

```
requireMention  streaming  showToolResults  debug
provider  model  preset  reasoningEffort
groupPrompt  directPrompt
access  admin  proactive  people  antiRepeat  stickers
replyDelayMs  replyDelayPerCharMs  replyDelayJitterMs  replyDelayMaxMs
```

> 白名单以代码为准（`src/setup/bind-routes.ts` 的 `EDITABLE_CONFIG_KEYS`），
> 这份清单只是速查。新增可编辑字段时必须同步两处：白名单 + `EDITABLE_CONFIG_SCHEMAS`。

每个键还有一个服务端 Schema 校验（`EDITABLE_CONFIG_SCHEMAS`）——**安全边界在宿主**，
客户端校验只是体验。

两个细节容易踩：

- **嵌套对象整体替换**：`access` / `admin` / `proactive` / `people` / `antiRepeat` / `stickers`
  提交时是整块覆盖，不是深合并。面板因此始终提交完整对象，不会写出「混合态」。
- **写配置会触发宿主热重载**，进行中的机器人会话会重置。

## 本地数据

```
<HOME>/.dsh-qqbot/                 ← 单实例（不传 settingsNs）
├── proactive-scores.jsonl   # 自主接话判定日志（含时机特征）
├── middleware-drops.jsonl   # 中间件链丢弃留痕（drop / denied / merge）
├── raw-events.jsonl         # 未知网关事件（探测「戳一戳」等平台事件是否推送）
├── startup.log              # 插件启动留痕（失败原因）
├── people.json              # 群友档案（昵称 / 别名 / 互动次数）
├── stickers.json            # 表情包图库元数据（素材在 stickers/ 子目录）
├── stickers/                # 表情包图片素材（需自行导入，仓库不含）
└── model-prefs.json         # per-peer 模型与预设偏好（偏好与实际 preset 分开存）

<HOME>/.dsh-qqbot/<settingsNs>/    ← 多实例时每实例一层
└── （同上，各自独立）
```

**多实例时按 `settingsNs` 分目录**：多个机器人是不同的"人"，
对群友的称呼与亲疏应当各自独立，不能共用一份档案。
`people` / `stickers` 的进程内单例也**按 ns 分实例**（否则同进程内会串）。

`startup.log` 是特意加的：宿主把插件加载错误打进自己的 stdout，桌面端取不回来，启动失败时这里能留痕。

`raw-events.jsonl` 用来回答「平台到底推不推某类事件」：让某人做一次那个动作，看有没有记录即可，不必猜。

`middleware-drops.jsonl` 用来回答「消息是不是被链上某个关卡丢掉了」：
门控有记录但 `people.json` 没更新时，先看这里。三类：
`drop`（消息没进 agent）、`denied`（命令被拒）、`merge`（N 条并成 1 轮）。

### 各文件的证明力

| 文件 | 写入时机 | 能证明什么 |
|---|---|---|
| `startup.log` | 插件 `apply()` | 插件**加载**了 |
| `proactive-scores.jsonl` | 门控判定时 | 消息**到达门控**了 |
| `middleware-drops.jsonl` | 链上短路 / 合并时 | 消息**被丢弃或合并**了 |
| `people.json` | `handleInbound` 内部 | 消息**穿过整条中间件链**了 |
| 会话事件日志 | agent 收到消息时 | 模型**被调用**了 |

## 开发模式的两条路

| 依赖写法 | 语义 | 适用 |
|----------|------|------|
| `file:<目录>` | 按发布物安装（打包 + 跑 `prepare` 构建） | 验证 `.npmignore` 裁剪是否正确 |
| `link:<目录>` | 软链到源码目录 | **开发模式**：构建完即刻生效 |

包管理器对 `file:` 目录依赖**不跟踪内容变更**——改完源码不会自动重新打包，`pnpm install` / `--force` / `pnpm add` 都无效。开发时一律用 `link:`。

### 改完代码要重启**宿主进程**

`link:` 让构建产物即刻可用，但 **Node 有模块缓存**——同一个模块路径再次 import 会直接返回缓存，
所以「重载插件」不保证换上新代码。可靠的只有重启整个应用：

```bash
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/restart-dsh.ps1
```

脚本会等 `startup.log` 出现新的 `apply()` 记录才算成功——**这一条才真正证明插件加载了**，
比「进程起来了」有意义得多。

QQ 机器人**不需要单独重启**：它只是插件里的一条 WebSocket 连接，
由插件自己 `bot.start()`，插件重新加载时自己重连。

## 宿主交互备忘

- 插件名 `im-qqbot`；bundle patch 里的行 id 也是 `im-qqbot`
- `inject = ['agents']`：宿主不提供 agents 服务则插件不激活
- 缺凭据时**不阻塞宿主 ready**：扫码流程异步进行，插件 fiber 立即进入 ACTIVE
- 写 profile 的 `cordis.patch.yml` 会触发宿主热更新（HMR），插件随之重载

## 测试与构建

```sh
pnpm build              # tsc（宿主半 → dist/）&& tsdown（浏览器半 → lib/client.js）
pnpm typecheck:client   # 浏览器半单独的类型检查
pnpm test               # vitest
```

两处容易忽略：

- **主 `tsconfig.json` 排除了 `src/client`**——浏览器半的类型错误只有 `typecheck:client` 能兜住。
  `pnpm build` 里的 `tsc` **不检查** `src/client`，CI 里因此单列了 `typecheck:client` 一步。
- **`vitest.config.ts` 显式限定 `include: ['src/**/*.test.ts']`**。不写的话 vitest 用默认通配，
  会扫到 `.tmp/` 下的临时副本，用例数翻倍、失败原因难定位。
