# 内部机制

本插件的架构与实现要点。想改行为前先读这里，能少踩很多坑。

## 一句话架构

> QQ 消息进 → 中间件链过滤与富化 → 组装成用户消息投给 dsh agent → agent 的 session 事件出 → 转成 QQ 消息发回。

宿主半（Node）与浏览器半（Web Bundle）分离：宿主半负责连接、协议、状态机；浏览器半只在设置页里渲染界面。

## 中间件链的顺序（关键）

顺序不是随便排的，改动前先理解每一步的职责：

| # | 中间件 | 作用 | 位置为什么重要 |
|---|--------|------|----------------|
| 1 | `errorHandler` | 错误兜底 | 最外层 |
| 2 | `messageFilter` | 去重 + 机器人回声过滤 | 按 `messageId` 去重，不会误杀不同群的同文消息 |
| 3 | `accessPolicy` | 白名单 / 开放 / 禁用 | — |
| 4 | `historyBuffer` | 群历史缓冲 | **必须在门控之前**：未点名她的群消息也要进上下文 |
| 5 | `mentionGate` | 记录 `wasMentioned` | 自主接话开启时改为 `passthrough`：只标记不拦 |
| 5.5 | `proactiveGate` | 自主接话判定与拦截 | **必须在 mentionGate 之后**：那里才写 `ctx.state.mention` |
| 6 | `contentSanitizer` | 去 @marker、表情标签、空白 | — |
| 7 | `rateLimiter` | 三层限流 | — |
| 8 | `slashCommand` | 斜杠命令 | 在并发守卫之前，命令不排队 |
| 8.5 | `questionAnswer` | 待答问题截获 | 同上，否则「等答案 ↔ 答案被缓冲」死锁 |
| 9 | `concurrencyGuard` | 同 peer 串行 + 消息合并 | 按 `scope:targetId` 隔离，不同群互不影响 |
| 10 | `typingIndicator` | 输入中提示 | — |
| 11 | `quoteRef` | 引用消息解析 | — |
| 11.5 | `attachmentProcessor` | 附件下载 | — |
| 12 | `envelopeFormatter` | 上下文组装（history + quote + sender） | — |

**改中间件顺序前先看这张表**。`proactiveGate` 与 `mentionGate` 的相对位置尤其关键：反了就读不到 `wasMentioned`，自主接话会永远判成「被点名」或「完全没被点名」。

## 会话隔离

会话键：

```
qqbot:${appId}:${kind}:${peerId}
```

- `kind`：`c2c`（私聊，peerId = 用户 openid）| `group`（群聊，peerId = 群 openid）
- 私聊与群是**两条独立会话**：在群里聊过的上下文不会带到私聊
- 群历史缓冲另有独立键（`${appId}:${groupOpenid}`），回复后清空，避免下次组包重复

## 预设固定

会话**固定**跑在 `qqchat` 预设上，三层锁死：

1. `config.ts` 的 `FIXED_PRESET_ID = 'qqchat'`
2. `session-manager.ts` 的 `getEffectivePresetByKey()` 恒返回它（不读 per-peer 覆盖，也不读 session 当初记录的 preset）
3. `/preset` 命令只做只读展示，明确拒绝切换

预设定义在插件自带的 `cordis.patch.yml`（`preset-qqchat` 插入行）里，用户装上即生效；profile 层仍可按同 id 覆盖。

`qqchat` 的要点：**不挂 `persistent-shell`（bash/pwsh）与 `tool-fs`**，工具清单里没有终端、没有文件读写；`persona.complete=true` 表示那段 prefix 直接作为完整 system prompt。

## 拟人化的三处落点

| 能力 | 位置 | 做法 |
|------|------|------|
| 不每条都回 | `shared/skip-marker.ts` | 回复恰为 `[skip]` → 不发送、不计入回复统计 |
| 不秒回 | `transport/reply-delay.ts` | 基础 + 每字 + 随机抖动，封顶可控 |
| 不复读自己 | 尚未实现 | 见 [拟人化路线图.md](拟人化路线图.md) 的 M7 |

前两条的开关都在设置页里（「QQ 机器人 → 自主接话 / 回复节奏」），改完自动重载。

## 设置页能改什么

宿主半的 `setup/bind-routes.ts` 里有一份**可编辑配置白名单**（`EDITABLE_CONFIG_KEYS`），
白名单外的字段只能改 `cordis.patch.yml`：

```
requireMention  streaming  showToolResults  debug
provider  model  preset
groupPrompt  directPrompt
access  proactive
replyDelayMs  replyDelayPerCharMs  replyDelayJitterMs  replyDelayMaxMs
```

每个键还有一个服务端 Schema 校验（`EDITABLE_CONFIG_SCHEMAS`）——**安全边界在宿主**，
客户端校验只是体验。

两个细节容易踩：

- **嵌套对象整体替换**：`access` 与 `proactive` 提交时是整块覆盖，不是深合并。
  面板因此始终提交完整对象，不会写出「混合态」。
- **写配置会触发宿主热重载**，进行中的机器人会话会重置。

## 本地数据

```
<HOME>/.dsh-qqbot/
├── proactive-scores.jsonl   # 自主接话判定日志
├── startup.log              # 插件启动留痕（失败原因）
└── model-prefs.json         # per-peer 模型与预设偏好
```

`startup.log` 是特意加的：宿主把插件加载错误打进自己的 stdout，桌面端取不回来，启动失败时这里能留痕。

## 开发模式的两条路

| 依赖写法 | 语义 | 适用 |
|----------|------|------|
| `file:<目录>` | 按发布物安装（打包 + 跑 `prepare` 构建） | 验证 `.npmignore` 裁剪是否正确 |
| `link:<目录>` | 软链到源码目录 | **开发模式**：构建完即刻生效 |

包管理器对 `file:` 目录依赖**不跟踪内容变更**——改完源码不会自动重新打包，`pnpm install` / `--force` / `pnpm add` 都无效。开发时一律用 `link:`。

## 宿主交互备忘

- 插件名 `im-qqbot`；bundle patch 里的行 id 也是 `im-qqbot`
- `inject = ['agents']`：宿主不提供 agents 服务则插件不激活
- 缺凭据时**不阻塞宿主 ready**：扫码流程异步进行，插件 fiber 立即进入 ACTIVE
- 写 profile 的 `cordis.patch.yml` 会触发宿主热更新（HMR），插件随之重载

## 测试与构建

```sh
pnpm build              # tsc（宿主半 → dist/）&& tsdown（浏览器半 → lib/client.js）
pnpm typecheck:client   # 浏览器半单独的类型检查
pnpm test               # vitest
```

两处容易忽略：

- **主 `tsconfig.json` 排除了 `src/client`**——浏览器半的类型错误只有 `typecheck:client` 能兜住。
  `pnpm build` 里的 `tsc` **不检查** `src/client`，CI 里因此单列了 `typecheck:client` 一步。
- **`vitest.config.ts` 显式限定 `include: ['src/**/*.test.ts']`**。不写的话 vitest 用默认通配，
  会扫到 `.tmp/` 下的临时副本，用例数翻倍、失败原因难定位。
