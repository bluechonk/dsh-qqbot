# 群友档案（记忆）—— 无工具方案

让机器人**记住每个群友**：他是谁、聊过什么、他在意什么。

> 状态：**实施版**（2026-10-24 定稿）。方向已确认：**无工具版先行**，
> 工具版另案。相对初版改了三处（摘要输入含模型回复 / 删 `summarizedUpToSeq` 断点 /
> 维护技能已完成），详见第五、七、十一、十五节。
> 实施计划在 `.planning/2026-10-24-people-memory/`，走 `feat/people-memory` 分支。
>
> **本文件的前提是「qqchat 零工具」**：模型没有工具通道，所以积累记忆的主动权
> 必须在插件手里（异步摘要）。
>
> 另有一份 [群友档案-工具版.md](群友档案-工具版.md)：前提是**预设允许工具**
> （只挂 `dsh-tools` 注册表、不挂 bash/fs/web），模型自己调 `remember` / `recall`。
> 两者共用同一份存储结构，**建议的落地形态是混合**——见工具版第七节。

## 一、现在的问题

`~/.dsh-qqbot/people.json` 里每个人的档案只有：

```json
{
  "openid": "EC16...",
  "name": "bluechonk",
  "aliases": [],
  "count": 8,
  "firstSeen": 1792725125501,
  "lastSeen": 1792752174754
}
```

注入给模型的只有一句：`【群友档案】他叫 bluechonk，你们聊过 8 次，算是熟人了。`

**这等于没有记忆**，两个原因：

1. **「聊过 8 次」是计数，不是内容**。模型知道聊过几次，但不知道聊了什么、
   他在意什么、上次说到哪儿了。
2. **对话内容只活在 dsh session 里，而 session 会消失**。长聊天会自动压缩
   （`compaction`），压缩后旧对话变成摘要、细节丢失；会话闲置超时会被回收；
   `/new` 直接清空。**聊得越久，记住的越少**——这是当前的确定行为，不是偶发。

第二条是关键：**记忆的价值恰恰是「对抗上下文丢失」**。
所以它必须落在 session 之外的文件里，且必须在 session 消失**之前**写下去。

## 二、目标

1. 每个群友一份**持久化记忆**：称呼、聊过的话题、他的偏好 / 处境 / 梗
2. **不依赖 session**：压缩、回收、换模型、重启都不丢
3. 能**注入上下文**，让模型「认得这个人」，而不是每轮从零开始
4. 在**零工具预设**下也能积累（见下节）
5. 成本可控、可关闭、失败不影响正常对话

## 三、硬约束：零工具

`qqchat` 预设只挂 `persona` + `compaction`，**零工具**；persona 里还明写
「没有任何工具可用：不执行命令，不读写文件」。

**所以「让模型调用 remember() 工具」这条路走不通。** 这是第四次撞上同一条约束：

| 功能 | 原设计 | 实际 |
|---|---|---|
| M4 群友档案 | 给模型工具「记住他」 | 无通道 → 本地启发式抽别名 |
| M5 表情包 | `send_sticker` 工具让模型选图 | 无通道 → 插件自主配图 |
| 图片理解 | `qqbot_describe_image` 工具 | 无通道 → 插件直接把图附给模型 |
| **长期记忆** | 模型自己决定记什么 | **无通道 → 插件侧摘要（本设计）** |

结论：**积累记忆的主动权必须在插件手里**，模型只负责「说」，不负责「记」。

## 四、方案：插件侧异步摘要

```
对话进行中
   │
   ├─ 每 N 轮 / 会话回收前 / /new / 关闭前   ← 四个触发点
   │        │
   │        ▼
   │   取出「与这个人」的最近对话（从 session 事件里）
   │        │
   │        ▼
   │   插件调 LLM 做一次「记忆更新」→ 返回一组短事实（JSON）
   │        │
   │        ▼
   │   写进 people.json 的 memory.facts（去重 + 封顶）
   │
   ▼
下一轮注入：【关于他】养了只叫豆豆的猫；在准备考研。
```

三个决定：

1. **谁摘要** → 插件（不是模型）
2. **什么时候摘要** → 四个「对话即将消失」的时机（第六节）
3. **摘要成什么** → 一组短事实，不是一段越长越长的摘要（第五节）

## 五、记忆结构

`people.json` 向后兼容地扩展（老文件没有 `memory` 字段照常工作）：

```ts
interface PersonProfile {
  // ── 现有字段（不动）──
  openid: string;
  name?: string;
  aliases: string[];
  count: number;
  firstSeen: number;
  lastSeen: number;

  // ── 新增 ──
  memory?: {
    /** 结构版本，便于将来迁移 */
    version: 1;
    /** 事实条目，一句一条 */
    facts: MemoryFact[];
    /** 上次摘要时间 */
    summarizedAt?: number;
  };
}

interface MemoryFact {
  /** 一句话，短、事实性（「养了只叫豆豆的猫」） */
  text: string;
  /** 记下的时间 */
  at: number;
  /** 来源：模型摘要 / 本地启发式 */
  source: 'summary' | 'heuristic';
}
```

**为什么是「事实列表」而不是「一段摘要」**：

| | 事实列表 | 一段摘要 |
|---|---|---|
| 注入长度 | 可只挑最近 N 条，**有上界** | 越写越长，最后没法注入 |
| 更新 | 追加 / 去重，不动历史 | 每次要重写整段，容易越写越糊 |
| 淘汰 | 可按时间或重要性丢单条 | 只能整段重来 |
| 可解释 | 每条独立可读 | 一段话里混着新信息和旧信息 |

**封顶与去重**：

- `facts` 最多 8 条（`people.memory.maxFacts`），超出按「最久未被重新确认」淘汰
- 写入前做一次相似度去重（复用 `anti-repeat/format.ts` 的 bigram Jaccard，
  阈值调高到 0.85）：同一件事反复说，只更新时间戳、不新增条目
- **不做「已摘要到第 N 条」的断点**（初版的 `summarizedUpToSeq` 已删）：
  compaction 会重排事件序号，断点会错乱。幂等完全靠上面的去重——
  同一段对话被重复摘要，产出的相似事实由去重吸收，而不是靠断点跳过

## 六、触发时机

| 时机 | 为什么是它 |
|---|---|
| **每 N 轮**（默认 8） | 长会话中途也要落袋，否则压缩时丢。N 轮是「内容够多值得摘」与「调用别太频」的折中 |
| **session 被回收前**（闲置超时） | 对话结束了，这是最后一次拿到完整内容的机会 |
| **`/new` / 会话重建** | 用户主动清空上下文，记忆必须留下 |
| **插件关闭前** | 同 `people.json` 的 flush 理由：内存里的东西不写盘就没了 |

四个触发点的共同点：**都卡在「对话即将消失」的边上**。
这不是巧合——记忆的唯一价值就是对抗上下文丢失，所以触发点必须贴着丢失的边界。

**摘要是异步的，不阻塞回复**：

- 在 turn 结束后跑，不占用户等待时间（陪聊场景对延迟敏感）
- 同一个人同时只允许一个摘要任务在跑（并发守卫）
- 失败只 `warn`，不影响对话，也不写半截数据

## 七、摘要怎么调

**输入**（都要裁剪，防爆 token）：

- 这个人最近 N 轮对话（取 `user/message` 与 `assistant/message`，
  **含机器人的回复**——模型回了什么本身就是「什么值得在意」的信号）
- 单条截断（如 200 字）、总长封顶（如 4000 字）
- 现有的 `memory.facts`（让模型知道「已经记过什么」，避免重复记）

> 事件来源用 `agent.session.snapshotEvents()`（DSH 官方读法），不自己解会话文件。

**输出**：**JSON 数组**，每项一句短事实

```json
{ "facts": ["养了只叫豆豆的猫", "在准备考研"] }
```

**解析失败就整批丢弃**，不猜、不半途写入；丢弃必须 `logger.warn` 留痕——
静默丢弃是本项目最贵的 bug。

**提示词要点**：

- 只记**关于这个人**的、**长期有用**的
- 不记寒暄、不记当次临时话题、不记机器人自己的事
- 没有新信息就返回空数组（**允许什么都不记**——这比硬凑一条更重要）
- 给一两个 few-shot 例子（正例 + 反例）

**用哪个模型**：可配置 `people.memory.provider` / `model`，留空用当前会话模型。
建议配一个**便宜模型**——摘要是后台任务，不需要聪明。

## 八、怎么注入

在现有档案行下面追加一行：

```
【群友档案】他叫老王，你们聊过 12 次，算是熟人了。
【关于他】养了只叫豆豆的猫；在准备考研。
```

- 只注入**最近 5 条**（`people.memory.injectFacts`），单条截断
- **群聊里更克制**：群聊注入 2 条，私聊 5 条
  ——沿用现有 `isGroup` 的取向（群里别像查户口）
- 位置：紧跟档案行，仍在 user 消息的旁白区（与现有设计一致，见 `docs/内部机制.md`）

## 九、配置

```ts
interface PeopleConfig {
  enabled: boolean;          // 现有
  maxAliases: number;        // 现有

  /** 长期记忆 */
  memory: {
    enabled: boolean;        // 默认 true（主人拍板默认启用）
    /** 每几轮摘一次 */
    summarizeEveryTurns: number;   // 默认 8
    /** 保留多少条事实 */
    maxFacts: number;              // 默认 8
    /** 注入多少条 */
    injectFacts: number;           // 默认 5（群聊取 2）
    /** 摘要用模型（留空 = 跟随当前会话正在使用的模型） */
    provider: string;              // 默认 ''
    model: string;                 // 默认 ''
    /** 单次摘要输出上限 */
    maxTokens: number;             // 默认 512
    /** 单次摘要输入上限（字） */
    maxInputChars: number;         // 默认 4000
  };
}
```

**默认启用**（主人拍板）：摘要跟随会话模型、走后台任务不阻塞回复，
效果不满意可随时 `enabled=false` 整体关闭。

## 十、成本与风险

| 风险 | 对策 |
|---|---|
| 额外 LLM 调用 | 每 N 轮一次 + 只在「对话将消失」时补一次；可整体关闭 |
| 摘要跑在回复关键路径上 | 异步、turn 结束后跑；失败只 warn |
| 摘要幻觉（记错人 / 记错事） | 只喂这个人的消息；提示词要求「只记明确说过的」；事实条目可人工删 |
| 记忆越记越脏 | 去重 + 封顶 + 每条带时间戳，可追溯 |
| 隐私（记的是别人） | 落盘在本地 `~/.dsh-qqbot/`；文档写明；提供清除方式（删 key 或整个文件） |
| 注入变长挤占上下文 | 注入条数有上界，单条截断 |

## 十一、工具 / 技能这两条路的可行性

你提到「可以加入一个群友档案的 skills 或者 tools 设计」，两条路分开看：

### 给**模型**加工具 —— 走不通

`qqchat` 零工具，persona 还明写「不读写文件」。除非换到有工具的预设
（那就不是零工具了），否则模型拿不到任何工具通道。**本设计因此选了插件侧摘要。**

### 给**主人 / 维护 agent** 加技能 —— **已实现**（2026-10-23）

`qqbot-people` 技能已落地并验证（`.agents/skills/qqbot-people/scripts/people.mjs`）：
`list` / `show <openid|名字|别名>` / `forget <目标> <片段>` / `export` / `path`，
已兼容本设计的 `memory.facts`（显示条数、按片段删除）。
用法见 `.agents/skills/qqbot-people/SKILL.md`。

> 注意：插件把档案缓存在内存里，收到新消息后 5 秒内整份写回——
> 改档案要趁群里安静时，改完 `show` 再确认一次。

## 十二、验收

| 验什么 | 怎么做 | 期望 |
|---|---|---|
| 能记住 | 私聊说「我养了只猫叫豆豆」，聊几轮后开 `/new` 再问「我养的猫叫什么」 | 答得出「豆豆」 |
| 抗压缩 | 长聊到触发压缩，再问早期说过的个人信息 | 仍记得 |
| 抗重启 | 记住后重启 DSH，再问 | 仍记得 |
| 不记寒暄 | 只闲聊几句 | `memory.facts` 不增长（允许空数组） |
| 记错能修 | 手动改 `people.json` 删一条 | 下次注入不再出现 |
| 群聊克制 | 群里观察注入 | 只带 2 条，不像查户口 |
| 可关闭 | `people.memory.enabled=false` | 完全不做摘要、不注入 |

## 十三、不做的事

- **不做向量检索**：事实条目少（≤8 条），直接全注入比检索更简单也更准
- **不做跨群共享**：同一个人在 A 群和 B 群是两份档案——与现有
  `(appId, scope, openid)` 隔离一致（两个机器人、两个群里的「他」本来就不同）
- **不记群聊里别人的事**：只记「跟这个人」有关的
- **不记机器人自己的事**：那是 `anti-repeat` 的活
- **不做自动遗忘**（除了封顶淘汰）：删除交给主人显式操作

## 十五、实施细节（2026-10-24 补）

**模块落点**：

| 关注点 | 文件 | 说明 |
|---|---|---|
| 结构与纯逻辑 | `src/features/people/memory.ts`（新）+ `store.ts` 扩展 | `MemoryFact`、去重、封顶、注入行渲染 |
| 摘要调用 | `src/features/people/summarizer.ts`（新） | 提示词、LLM 调用、JSON 解析、失败丢弃 |
| 触发接线 | `src/gateway/bootstrap.ts` + session 生命周期 | 四个触发点，异步、并发守卫、留痕 |
| 注入 | `format.ts` + `transport/inbound.ts` | 档案行下追加「【关于他】…」，仍走旁白区 |

**摘要提示词具体化**（第七节的落地形态）：中文输出 JSON `{"facts": ["…"]}`；
只记关于**当前对话者本人**的长期事实；不记寒暄、当次情绪、机器人自己的话；
没有新信息返回 `{"facts": []}`；带一组正反例 few-shot。

**并发与留痕**：同一个人同时只允许一个摘要任务在跑（守卫表放内存）；
每个失败分支（LLM 报错 / JSON 解析失败 / 空结果）都 `logger.warn` 留痕。

**测试清单**：去重阈值边界、封顶淘汰顺序、注入条数（群 2 / 私 5）、
解析失败整批丢弃、向后兼容老档案、并发守卫、`enabled=false` 零副作用。
