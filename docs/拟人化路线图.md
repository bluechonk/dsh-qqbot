# 拟人化路线图 — 让大肥鱼在 QQ 群里像真人

> 目标：不是「功能更多」，而是**像群里一个真人**。
> 判据很简单——把她的发言混进群聊记录里，**看不出哪条是机器人发的**。
>
> 本文是对现状的差距分析与实施计划。必做 = 决定「像不像真人」的核心；可做 = 锦上添花。

## 三、必做清单

> 判据：不做这一项，一眼就看出是机器人。

### M1. 择机发言（择时 + 门控） — 核心

> **状态：未实现。** 价值门控（哪条值不值得接）已做完，只剩时机特征这一半。

**做什么**：在「这条话值不值得接」之上，再加「**现在是不是好时机**」。

**方案**（扩展 `src/features/proactive/lexical-gate.ts`）：

| 特征 | 方向 | 说明 |
|---|---|---|
| 群内近 3 分钟消息数 | 热闹 → 降权 | 别人正聊得欢，别插嘴 |
| 群内沉默时长 | 冷场 → 升权 | 冷了很久，出来起个头是真人行为 |
| 同一人连续发言 | 降权 | 不是在跟你说话 |
| 这条是否在回应别人 | 降权 | @了别人是别人的场子 |
| 话题类型 | 升/降权 | 情感/求助类接，事务/技术类不接 |

**验收**：群里连发 20 条闲聊，AI 被唤醒 ≤ 3 次；冷场 10 分钟后出现一条抱怨，她会接。

### M2. 沉默机制（允许不回） — ✅ 已实现

**做什么**：AI 在回合内可以决定「这一条我不回」。

**实现**：`src/shared/skip-marker.ts` 识别约定标记（正文恰为 `[skip]`）→ 不发送、不计入回复。

**为什么必做**：真人不会每条都回。只会回 = 一眼机器人。

**验收**：AI 判断不该接时，QQ 侧零消息；日志里能看到「本轮选择沉默」。

### M3. 回复延迟（拟人节奏） — ✅ 已实现

**做什么**：回得不那么快。

**实现**：`src/transport/reply-delay.ts`，发送前加一个可配的延迟：

```
delay = clamp(baseMs + 字数 * perCharMs + 随机抖动, minMs, maxMs)
默认 baseMs=1200, perCharMs=80, 抖动 0~1500ms，上限 8s
```

**为什么必做**：**这是投入产出比最高的一条**。0.2 秒秒回是机器人的最强特征；改成 2~6 秒后拟人感立刻上一个台阶。成本不到 20 行代码。

**可配**：**顶层**配置 `replyDelayMs` / `replyDelayPerCharMs` / `replyDelayJitterMs` / `replyDelayMaxMs`
（**注意不在 `proactive` 块内**——`proactive` 只管「要不要接话」，延迟是出站的事）。
设置页「QQ 机器人 → 回复节奏」可直接改。

### M4. 群友档案 — 已实现（v1）

**做什么**：记得群里每个人是谁。

**已落地**（`src/features/people/`）：落盘 `~/.dsh-qqbot/people.json`，
按 `appId|群或私聊|openid` 隔离——同一个群被两个机器人加，档案各自独立。

```json
{
  "openid": "EC1625...",
  "name": "bluechonk",
  "aliases": ["主人"],
  "count": 12,
  "firstSeen": 1792603205000,
  "lastSeen": 1792603205000
}
```

**关键取舍：档案只能靠本地启发式积累。**
qqchat 是**零工具**预设，模型没法调用「记住他」这类工具，
所以别指望模型自己写档案——只能从消息信封取昵称、
从「叫我X / 我是X / 我叫X / 喊我X」抽别名，且**宁缺毋滥**
（「我是说你搞错了」不能被记成别名「说你搞错了」，认错称呼比不认更尴尬）。

**v1 未做**：`style`（说话风格）、`memes`（口头禅）、`affinity`（好感度）——
这三项都需要模型参与判断，与「零工具」冲突，留待有工具通道时再说。

<details>

```json
{
  "openid": "EC1625...",
  "name": "bluechonk",
  "alias": "主人",
  "style": "短句、爱逗她",

```

**关键**：每次群消息把「说话人是谁 + 亲疏」拼进 user message（`[昵称(备注) · 关系近]`）。

**为什么必做**：**叫得出名字 = 拟人感最直接的来源**。真人会喊你外号，机器人只会说「主人」。

**注意**：这与「记忆用户说了什么」是两件事——档案是**结构化的、少的、稳的**；记忆是**自由文本、多、易过期**。别混。

### M5. 表情包 — 未实现

见第四节专门设计。

### M6. 句式稳定（口头禅 / 句式库） — 已实现

**做什么**：每次回复的句式不重样，但风格一致。

**现状问题**：persona 写死「40 字以内」很死板，模型容易每次都「哼，……」开头。

**已落地**：cordis.patch.yml 的 qqchat persona 里加了「说话方式」分组——
被叫到 / 被夸 / 被冷落 / 关心人 / 吐槽 / 收尾 各 3 条，
并要求「每次只挑一条，别堆砌」，末尾再补一句「同一句话不要连着说第二遍」。

**为什么必做**：复读机是 LLM 群聊最大的扣分项，比不拟人更劝退。

### M7. 防复读（自己说过的话不重复） — 已实现（预防式）

**做什么**：不重复自己刚说过的话。

**已落地**（`src/features/anti-repeat/`）：按会话记自己最近 5 条发言（纯内存），
每次组装消息时把「【你最近说过】…换个说法，别让人觉得你在复读」前置给模型。

**关键取舍：预防式，不做事后纠正。**
原方案是「生成后算相似度，超阈值就回灌让它重写」——那要多跑一轮模型，
延迟与 token 都翻倍，而陪聊场景对延迟极敏感。
预防式只要把最近说的话放进上下文，模型自己就会换说法，**零额外开销**。

相似度判定（`similarity()`）仍保留：字符 bigram 的 Jaccard，阈值 0.72，
可用于观测「她是不是真的在复读」。选 bigram 而非 3-gram 是因为中文短句下
3-gram 区分度不足；抹掉标点是因为语气差别不该算「不同说法」。

**未做**：检查与群友发言是否重复（复读群友更劝退，但需要历史窗口配合）。

**为什么必做**：同上，复读机。

### M8. 主动起话题（冷场启动） — 未实现

**做什么**：群里冷场了，她偶尔起个头。

**方案**：
- 触发：群内沉默 > `idleTriggerMin`（默认 20 分钟）且当日已起话题 < N 次
- 素材：群历史里未完的话题 / 表情包 / 主人近况 / 当天日期
- 出口：与 M1 门控共用，只是把「门控」换成「冷场加成」

**为什么必做**：这是「主动参与」的高阶形态，也是群里最像真人的行为（真人会救场）。

## 四、表情包专项设计

### 4.1 对「导入时自动识别打标签」的审视

主人的想法：**导入时自动识别好，给每个表情包打 tag 和 desc**。

**方向对，但不该放在「导入时自动识别」这一步。** 三个理由：

1. **导入时没有语境，模型只能看图猜。** 一张梗图的意思往往在**梗的出处**里（哪次对话、哪个名场面），看图猜出来的 desc 经常是错的（把「我能去你家吃饭吗，就一碗」理解成「蹭饭」而不是「饥饿+自来熟」）。
2. **标签会过期。** 梗会过气，热词会换。导入时打的标，一年后一半是错的。
3. **成本与收益不匹配。** 每张图跑一次 VLM 描述 = 慢、贵，还要本地模型。

### 4.2 更好的方案：三层标签，各司其职

| 层 | 来源 | 什么时候产生 | 成本 | 质量 |
|---|---|---|---|---|
| **L1 语义描述** | **素材自带**（见 4.4） | 导入时直接读取 | **零** | **最高**（带梗背景与使用场景） |
| **L2 场景标签** | 人工批量指定 / 半自动聚类 | 导入时或事后 | 低 | 高 |
| **L3 检索向量** | 运行时算（CLIP / 文本嵌入） | 导入时一次 | 中 | 中（用于匹配，不用于理解） |

**L1 是关键**：最好的 desc 不是模型生成的，是**素材方已经写好的**。见 4.4。

**L2 标签体系（建议最小集）**：

- 情绪：`得意` `嘲讽` `委屈` `卖萌` `无语` `开心` `生气` `疑惑`
- 场景：`被夸` `被骂` `摸鱼` `干饭` `加班` `被冷落` `被戳` `得意忘形`
- 强度：`轻` `重`

标签集**故意做小**（8~10 个情绪 × 8 个场景），标签多了 AI 反而选不出来。

### 4.3 AI 怎么知道该发哪张 —— 检索 + 工具，而不是把图库塞进 context

**❌ 不能做**：把 1400 张图（哪怕只有台词）塞进 system prompt —— token 爆炸，且模型选不出来。

**✅ 该做**（分层）：

```
每轮对话：
  ① 把「当前情绪 + 最近 3 条群消息」编码成 query
  ② 混合检索：L2 标签硬过滤（可选） × L3 向量相似度排序 → 取 Top-K（K=8）
  ③ 把这 8 条的「台词 + desc + 情绪标签」写进一个**临时的候选清单**
  ④ 暴露工具 send_sticker
```

**工具设计**（两种模式都留）：

| 模式 | 参数 | 用途 |
|---|---|---|
| 精确选 | `send_sticker(id)` | AI 从候选清单里挑好了 |
| 描述意图 | `send_sticker(query="被夸了想得意")` | 插件自己再检索一次（扩大候选） |

**候选清单怎么进上下文**（两种）：

- **A. 作为工具描述的一部分** —— 简单，但每轮都占 token
- **B. 作为一条临时的 user message / prompt section** —— 语义更自然，AI 更容易"看着清单选"

推荐 **B**：把「【可发表情】当前可选：#12 得意「原来是高等模型」/ #52 嘲讽「你就是一只吃白饭的鲸鱼」/ …（只发一个，或不发）」作为一段 system prompt section 注入。

### 4.4 发送时机控制

真人不是句句发表情。规则：

| 规则 | 默认 |
|---|---|
| 连续 N 条文字回复最多配 1 个表情 | N=3 |
| 情绪不匹配时宁可不发 | 由 L2 标签与当前情绪比对 |
| 同一张表情不连发 | 冷却 10 分钟 |
| 不在严肃/工作话题发表情 | 话题分类过滤 |
| 表情包**替代**文字，而不是**追加** | 短场景下只发表情，不带文字 |

最后一条很关键：**真人发表情包常常只有一张图 + 零文字**。如果大肥鱼每次都是「文字 + 表情包」，反而假。

### 4.5 图库实现

```
~/.dsh-qqbot/stickers/
  index.json          # 元数据：id / 文件名 / 台词 / desc / tags / embedding
  images/             # 实际图片（webp/gif）
```

- 向量用本地算（可选依赖），没装就退化成**纯标签匹配**（不阻塞功能）

**版权处理（红线）**：

> 素材方明确：角色形象「蓝色大肥鱼 / 鲸鱼娘」与原始画作**版权归原作者及社区作者所有**，非营利粉丝向玩梗可用，**商用需自行评估**；站点与仓库均设有侵权举报入口（72 小时内下架）。

所以本项目的做法：

1. **代码只做通用图库能力**（导入 / 打标 / 检索 / 发送），**不在仓库里内置、不分发这批图**。

4. 若将来要内置「官方推荐包」，必须先拿到画师授权。

**这一条别省**——内置 1400 张图再分发，是明确的侵权风险。

### 4.7 关于「用 tools 设计」这个想法的结论

**主人的直觉是对的**（发图必须是一个动作 = 一个工具），但**不能只做工具**：

- 只有工具、没有检索 → AI 不知道有哪些图可发（1400 张塞不进 context）
- 只有检索、没有工具 → AI 没法表达「我想发那张」
- **检索 + 工具 + 临时候选清单** 三件套才是完整方案

## 六、实施顺序建议

```
第 1 轮（地基 + 立刻见效）
  ✅ M3 回复延迟   ← 20 行代码，拟人感提升最大      已完成
  ✅ M2 沉默机制   ← 与门控配套                    已完成
  ✅ 价值门控 L1   ← 词法打分 + 冷却 + 判定日志     已完成
  ⬜ M1 时机特征   ← 在门控上加时间/热度维度
  ✅ M4 群友档案   ← 已完成（v1：昵称 / 别名 / 互动次数）
  ✅ M6 句式库 + M7 防复读   ← 已完成

第 2 轮（表情包）
  ⬜ 图库结构 + 导入向导 + L1/L2 标签
  ⬜ send_sticker 工具 + 临时候选清单
  ⬜ 发送时机控制
  （先导 20~30 张手选，验证体验后再扩量）

第 3 轮（主动性）
  ⬜ M8 冷场起话题
  ⬜ 群角色定位 / 作息 / 主动私聊
  ⬜ 长期记忆 / 跨群记忆
```

**下一步的排序理由**：

1. **M4 群友档案**排最前——「叫得出名字」是拟人感最直接的来源，且它是 M1/M6/M7 的共同输入（知道是谁、知道说话风格，才谈得上防复读与句式）
2. **M1 时机特征**次之——它直接决定「她会不会在该出现的时候出现」，实现成本也低（门控里加时间维度）
3. **M7 防复读 + M6 句式库**——复读机是 LLM 群聊最大的扣分项，但需要 M4 的发言流水打底

## 七、与上游 / 参考实现的关系

| 来源 | 用在哪 | 归属要求 |
|---|---|---|
| tencent-connect/dsh-qqbot | 全部基础代码 | MIT，README 顶部注明上游来源、LICENSE 保留原版权 |
| zaofan-make/dsh-qqbot | **仅参考机制**：价值门控（KNN + 样例库）、插话注入、纯主动出站降级链、表情包库的存取与检索思路 | MIT；若**直接引用源码**，须在 README 致谢并在 LICENSE 附注。**优先自研等价实现**（见下） |
| dsh-mcp-manager / dsh-skills-manager | **家风格**：README 与文档结构、单文件 client、只用 `--dsw-alias-*` 令牌、类名统一前缀、i18n、market-index、CI | 自家插件，直接对齐 |

**关于 L1 门控为什么自研**：zaofan 用的是「KNN + 样例库」的相似度门控，要维护样例集与嵌入；本项目选了**纯词法打分**——零依赖、零 token、纯函数便于单测，代价是精度不如 KNN，但配合 L2 模型自决已经够用。等有了 `people.json`（M4）与时机特征（M1），再考虑是否引入嵌入。

**关于「参考 vs 借鉴」的取舍原则**（主人要求：参考了他的源码要加 README 与 MIT）：

1. **能自研等价实现的，一律自研**——例如表情包的检索与发送，官方插件本来没有，zaofan 的实现是另一套架构（780KB 手写 bundle + 780 张库的体量），照搬会带进大量我们不需要的东西。
2. **确实要引用的代码**，才在 README 加「致谢」段并在 LICENSE 附注原项目与许可。
3. **只读机制不抄代码的**（如价值门控的思路），在设计文档里注明出处即可。
