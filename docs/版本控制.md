# 版本控制设计

本仓库的版本控制约定。**先读这一份，再动手改代码。**

## 一、仓库拓扑

| 项 | 值 |
|---|---|
| 本地路径 | `C:\Users\bluechonk\Documents\deepseek-harness\default-workspace\dsh-qqbot` |
| `origin` | `https://github.com/bluechonk/dsh-qqbot.git`（自有仓库，MIT） |

### 为什么 main 是「单根提交」

本仓库是从官方代码**重建**的，不是普通 fork：

- 官方 commit 历史**不保留**（主人明确要求「代码直接用官方改造，不要保留原官方的 commit 记录」）
- 根提交 `4ad4afe` 的父提交数为 0（orphan 分支取 upstream/main 的代码树）
- 因此 `main` 与 `upstream/main` **没有共同祖先**，`git merge-base` 返回空

推论：**不能**用 `git rebase upstream/main` 或 `git merge upstream/main` 来同步上游——
没有共同祖先的 merge 会把两段无关历史缝在一起。同步上游只能**手工搬运**需要的改动。

### 已废弃分支

`feat/proactive-group-chat`（本地与 `origin` 都有）是重建**之前**的旧分支，
与 `main` 无共同祖先，内容已被重建后的 `main` 完全取代。

| 分支 | 状态 | 处置 |
|---|---|---|
| `feat/proactive-group-chat` | 废弃 | 不再使用；删除属破坏性操作，需主人确认后再删 |

> 判断依据：`git log --oneline main..<branch>` 列出的提交（如 `7b84c88 docs(proactive)`）
> 在 `main` 上都有等价物（`docs/自主接话.md`）。

## 二、分支模型

```
main ──────────────────────────────────────────────▶  （唯一长期分支）
  │
  ├── feat/<模块>     功能开发        feat/admin、feat(preset)
  ├── fix/<模块>      缺陷修复        fix(session)、fix(model)
  └── refactor/<模块> 大重构          refactor/extensions
```

- 分支**从最新 `main` 创建**，禁止在 `main` 上直接做大改造
- 分支名用**模块名**而非描述：`feat/admin` 而不是 `feat/admin-whitelist`
- 合并后删除分支，保持 `git branch` 干净

## 三、什么时候直接推 main，什么时候开 PR

### 直接推 `main`

- 文档、注释、单文件修复
- 小改动（不跨模块、不动契约、预计 < 20 个文件）
- 已自测通过的功能增量

### 必须开 PR

命中**任一**即为「大改造」，先开分支再动手：

| 判定 | 例子 |
|---|---|
| 跨两个及以上包或模块 | 改 `session` + `model` + `commands` |
| 涉及目录结构、包边界、构建配置 | 新增 `src/features/*` 顶层模块 |
| 涉及契约、存储落点、对外 API 或模型 id 形态 | 改 `model-prefs.json` 结构、改绑定路由 |
| 需要迁移或回滚 | 偏好文件加字段 |
| 预计改动超过 20 个文件 | — |

**大改造动手前必须先出方案**：目标、影响范围、迁移路径、验证方式、回滚方式。
方案写入计划文件（见第六节），经主人确认后再动手。

### 累积提交什么时候推

| 情况 | 动作 |
|---|---|
| 一个逻辑变更完成且测试全绿 | 立即提交 |
| 累积若干提交、功能可独立运行 | 推 `main` |
| 大改造完成 | 开 PR，不直推 |

不在 CI 红着的时候推新提交。

## 四、提交规范

Conventional Commits 的中文版：`type(scope): 中文描述`

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档 |
| `style` | 格式（不影响代码含义） |
| `refactor` | 重构（既非新增也非修复） |
| `perf` | 性能 |
| `test` | 测试 |
| `chore` | 构建、依赖、杂项 |

规则：

1. `scope` **必填**，填变更涉及的模块或对象名（如 `admin`、`session`、`middleware`）
2. 描述用简体中文，**结尾不加句号**
3. **一次逻辑变更只产生一个提交**；能合并的改动不拆成多个 commit
4. 破坏性变更用 `!` 或 `BREAKING CHANGE:` 标注
5. 提交信息先写入项目根 `.tmp/commit-msg.txt`，再 `git commit -F .tmp/commit-msg.txt`
   ——多行或含引号的中文直接内联进 shell 会被转义破坏

示例：

```
feat(admin): 命令权限——管理员白名单
fix(session): 修两个让机器人彻底哑掉的静默故障
feat(middleware): 中间件链丢弃留痕——静默失效最大的盲区
```

## 五、版本号与更新日志

- 版本号在 `package.json` 的 `version`，当前 `0.1.0`
- **自用插件**：版本线固定在 `0.1.x`，接口、清单格式与界面都可能再改，不做兼容性承诺
- 真要改到不兼容，走 `0.2.0`（换一版设计）
- 等有别人开始依赖本插件的清单格式与接口，再考虑升 `1.0.0`
- 变更写入 [CHANGELOG.md](CHANGELOG.md)，按版本分节（新增 / 变更 / 修复 / 标识）
- 上游 `0.1.0 ~ 0.5.2` 的历史见其仓库，本仓库的 CHANGELOG 只记自己的变更

## 七、推送门禁

推送前必须全绿：

```bash
pnpm install --frozen-lockfile   # 锁文件与 package.json 一致
pnpm build                       # tsc（宿主半）+ tsdown（浏览器半）
pnpm typecheck:client            # 浏览器半单独类型检查
pnpm test                        # vitest
```

CI（`.github/workflows/ci.yml`）在 Node 22.x / 24.x 两条 matrix 上跑同样的四步。

- CI 红着时**不要**继续推新提交，先修绿
- 项目未装 pre-push 钩子；若将来加装，**不得用 `--no-verify` 绕过**

## 八、上游同步策略

`upstream` 是腾讯官方仓库，本仓库是其改造版。

| 场景 | 做法 |
|---|---|
| 需要上游的新能力 | 手工搬运对应改动，不要 merge 整个分支 |
| 上游修了我们也有同样 bug 的地方 | 对比后决定是否采纳，采纳则在本仓库的提交里注明来源 |
| 上游大版本升级 | 先评估影响（尤其 DSH 契约），再决定是否跟进 |

**不要** `git merge upstream/main`：两边无共同祖先，merge 会缝出两段无关历史。

## 九、回滚方式

| 场景 | 回滚 |
|---|---|
| 单个提交有问题 | `git revert <sha>`（保留历史，安全） |
| 未推送的本地提交 | `git reset --soft HEAD~1` 后重新提交 |
| 已推送且只有自己用 | 避免强推；确实需要时先说明，再 `git push --force-with-lease` |
| 配置写坏 | 配置在 profile 的 `cordis.patch.yml`，改回后设置页保存或重启 |

破坏性变更必须在提交信息里标注，方便日后定位。

## 十、仓库卫生

| 项 | 规则 |
|---|---|
| 换行 | 仓库文本一律 LF；`.gitattributes` 含 `* text=auto eol=lf` |
| 构建产物 | `dist/`、`lib/`、`node_modules/` 不入库 |
| 敏感信息 | 严禁提交 apikey / token / 密码 / 私钥 / 连接串；走环境变量 |
| 凭据文件 | `.env`、`.pem`、`.key` 一律 gitignore |
| 过程文件 | `.planning/`、`.zcode/`、`.tmp/` 一律 gitignore |
| 图片 | `.png` `.jpg` 等标 binary，避免行尾转换损坏 |
